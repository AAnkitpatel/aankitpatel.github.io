Migrating 20+ Microservices from EC2 to ECS Fargate

How a real-time gaming platform moved off self-managed EC2 with zero downtime — and what actually made the 40% cost cut and 85% faster releases possible.

Ankit Patel · W3Villa Technology · ~7 min read

At W3Villa I was the only DevOps engineer covering 20+ production platforms, including a real-time multiplayer gaming stack running as 20+ containerized microservices directly on EC2. It worked, but it was expensive to run and slow to change: every deploy meant hand-managing instance capacity, and scaling for traffic spikes meant either over-provisioning year-round or reacting late.

The problem with EC2 for this workload

The services were already containerized, which made EC2 the wrong layer to keep managing by hand. We were paying for peak capacity around the clock, patching and rotating instances ourselves, and deploys were slow enough that rolling out a fix under load was a genuinely stressful event. None of that is a knock on EC2 — it's just the wrong tool once you're already running everything in containers and need fast, low-risk releases.

Why ECS Fargate

We didn't need Kubernetes-level flexibility for this stack, and I didn't want to take on cluster operations as a team of one. ECS Fargate removed the EC2 fleet entirely — no AMIs to patch, no capacity to pre-provision — while keeping the container workflow the team already knew. Terraform became the single source of truth for the ECS services, task definitions, ALB target groups, and IAM roles, so every environment was reproducible instead of hand-built.

Architecture

The traffic path is a standard ALB-in-front-of-ECS-Fargate setup, but the piece that mattered most was the deploy path: Drone CI builds and pushes the image, then deploys to a second ("green") target group behind the same ALB. Traffic only cuts over after health checks pass, and the previous ("blue") target group stays warm for an immediate rollback if something looks wrong.

Color key: green = actively serving traffic, gray = standby target group.

What actually moved the numbers

  • Cost (−40%): Fargate billed per task instead of per always-on instance, and right-sizing task CPU/memory per service — instead of one EC2 instance size for everything — removed most of the over-provisioning we'd been carrying.
  • Deploy speed (−85%): blue-green through Terraform-managed target groups meant a release was a target-group swap, not a manual instance-by-instance rollout. What used to take a coordinated maintenance window became a routine CI job.
  • Zero downtime: the green target group only takes traffic after ALB health checks pass, and the blue group stays live in parallel, so a bad deploy is a target-group swap back, not an incident.

What I'd do differently

Fargate's per-task pricing rewards right-sizing, and I under-invested in that early — a couple of services ran over-provisioned for weeks before I went back through CPU/memory metrics per task and tightened them. If I were starting the migration again, I'd bake that review into the Terraform module from day one instead of treating it as cleanup afterward.
